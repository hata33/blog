### 心智模型

工具调用的前端渲染，核心是将 Agent 执行动作的“黑盒”过程，可视化为结构化的 UI 卡片。其运转逻辑是一个**生命周期驱动的状态机**：

1.  **数据统一**：后端 Agent 的工具调用和结果，被 `useStream` Hook 统一封装为 **`toolCalls` 数组**。数组中每个对象都遵循 `pending -> completed/error` 的明确生命周期。
2.  **消息关联**：通过 `call.id`，将每个工具调用对象与触发它的 AI 消息关联起来，确保卡片渲染在正确的对话位置。
3.  **UI 映射**：根据工具调用对象的 **`call.name` (工具名)** 和 **`state` (生命周期状态)**，在组件中通过 `switch/case` 或条件判断，来精准选择渲染加载、错误、成功或特定工具的专属卡片。

### 关键实践提示

*   **【核心】必须处理所有状态**：在为工具调用设计 UI 时，**务必覆盖 `pending`（加载）、`completed`（成功）和 `error`（失败）三种状态**。绝不能让用户看到空白的卡片，这是提供良好体验的底线。
*   **【安全/健壮性】安全解析结果**：工具执行的结果通常是字符串，使用 `JSON.parse()` 解析时**必须包裹在 `try/catch` 中**，并提供解析失败时的回退（fallback）UI，防止因非预期数据格式导致组件崩溃。
*   **【类型安全】利用类型系统**：如果你的工具是用 Zod 等库定义了 Schema，应使用 `ToolCallFromTool` 等工具类型来推导参数类型。这能在编译时为 `args` 提供类型安全，Schema 变更时立刻暴露错误。
*   **【架构】提供通用回退**：不需要为每个工具都创建专属卡片。对所有未知或不重要的工具名，渲染一个通用的、可折叠的 JSON 卡片即可，保证系统不会因未处理工具名而报错。
*   **【UX】加载态展示上下文**：在执行 `pending` 状态的加载卡片时，应明确展示**工具名称和参数**。这能既时告诉用户“Agent 正在做什么”，使其感知系统状态。
*   **【UX】处理并发调用**：Agent 可能同时调用多个工具。代码应能处理 `toolCalls` 数组中同时存在多个 `pending` 状态项，使它们各自独立解析和更新，互不干扰。
*   **【UX】更新模式**：工具调用是**原地更新**的，它在 `toolCalls` 数组中始终是同一个对象（通过 `id` 标识），只是其 `state` 属性会从 `pending` 变为 `completed` 或 `error`。前端组件据此进行状态的平滑过渡。
